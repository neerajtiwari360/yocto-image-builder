# Build on the PC and update a running KV260

Use this guide for a board running `kv260-vision-hdmi` (systemd). Application
updates do not require reflashing the SD card. Compile on the PC with the
matching Yocto ARM64 toolchain, transfer the package over UART, then restart
the affected service. The board image has no compiler or package manager and
does not provide network deployment by default.

## 1. Choose the source and update scope

| Change | Edit on the PC | Build component | Board service |
| --- | --- | --- | --- |
| ML application, preprocessing, inference or postprocessing | `D:\Github\FaceGuard\kv260-yunet\runtime\src\` | `ml` | `yunet-inference` |
| HDMI rendering/layout | `D:\Github\FaceGuard\kv260-yunet\runtime\src\hdmi\` | `hdmi` | `yunet-hdmi` |
| Compatible compiled model | `D:\Github\FaceGuard\kv260-yunet\runtime\model\` and its contract/manifest | `ml` | `yunet-inference` |
| Shared camera/IPC interface or both applications | Corresponding runtime source | `all` | Both services |
| Kernel driver, device tree, FPGA firmware or OS library | `D:\Github\yocto-image-builder\yocto\` | Full image | Reboot into updated image |

Application source is maintained in FaceGuard. Do not edit generated copies in
Docker's `/work` tree or inside `runtime.tar.gz` in this repository.
See [the application module guide](../../FaceGuard/kv260-yunet/MODULES.md)
for source ownership and interface contracts.

### Exact application files and their update commands

Paths in this table are relative to `D:\Github\FaceGuard\kv260-yunet`.
Use the build and transfer commands in sections 2 and 4 with the component
listed here; the source files themselves are not copied to the board.

| Code or setting to change | Maintained file | Component to build/deploy |
| --- | --- | --- |
| Main inference/capture loop | `runtime/src/app/main.c` | `ml` |
| ML configuration parsing | `runtime/src/app/config.c` | `ml` |
| Resize, letterbox and input quantization | `runtime/src/ml/preprocess/preprocess.c` | `ml` |
| VART runner and DPU model execution | `runtime/src/ml/inference/dpu_bridge.cpp` | `ml` |
| Detection decoding and NMS | `runtime/src/ml/postprocess/postprocess.c` | `ml` |
| Display mode, DRM/KMS and layout | `runtime/src/hdmi/hdmi.c` | `hdmi` |
| Preview drawing | `runtime/src/hdmi/preview_render.c`, `runtime/src/overlay/overlay.c` | `hdmi` |
| V4L2 capture or camera ownership | `runtime/src/camera/capture.c`, `camera_guard.c` | `all` |
| Shared frame/detection mailbox | `runtime/src/ipc/preview.c`, `runtime/include/preview.h` | `all` |
| Model and fingerprint/score/NMS configuration | `runtime/model/`, `runtime/config/yunet.conf` | `ml` |
| HDMI arguments | `runtime/config/yunet-hdmi` | `hdmi`, then explicitly install the config as described in section 5 |
| Inference launch command/unit | `runtime/scripts/run.sh`, `runtime/scripts/yunet-inference.service` | `ml`; explicitly install a changed unit |
| HDMI unit | `runtime/scripts/yunet-hdmi.service` | `hdmi`; explicitly install a changed unit |

For example, after editing `runtime/src/ml/preprocess/preprocess.c`, build
`-Component ml`, stop `yunet-inference` on the board, deploy `-Component ml`,
then restart `yunet-inference`. After editing `runtime/src/hdmi/hdmi.c`, use
`-Component hdmi` and `yunet-hdmi` instead.

## 2. Cross-compile on the laptop

Start Docker Desktop in Linux-container mode. Keep the existing Yocto workspace
volume; it contains the matching compiler, sysroot and build caches. A successful
HDMI image build prepares the platform used by the application build helper.

Run in **laptop PowerShell**, choosing one command:

```powershell
cd D:\Github\FaceGuard\kv260-yunet

# ML application and model:
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\Build-Runtime.ps1 -Component ml

# Or HDMI viewer only:
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\Build-Runtime.ps1 -Component hdmi

# Or both applications:
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\Build-Runtime.ps1 -Component all
```

The helper uses `D:/Github/yocto-image-builder` by default; supply
`-ImageBuilder <path>` if your checkout is elsewhere. It cross-compiles with
Yocto and copies the selected archive and checksum file into FaceGuard's
`kv260-yunet/deploy/` directory:

| Component | Archive | Checksum file |
| --- | --- | --- |
| `ml` | `yunet-ml-arm64.tar.gz` | `SHA256SUMS-ml` |
| `hdmi` | `yunet-hdmi-arm64.tar.gz` | `SHA256SUMS-hdmi` |
| `all` | `yunet-kv260-arm64.tar.gz` | `SHA256SUMS-all` |

Keep a copy of the last working archive before rebuilding; these filenames are
overwritten. Use a previous compatible archive for rollback.

## 3. Stop the selected component on the board

Open PuTTY on the board's actual COM port: **115200 baud, 8N1, no flow control**.
Log in as `root`. At the **board shell**, run the appropriate command:

```sh
# ML update: HDMI may remain running and show camera-only video.
systemctl stop yunet-inference

# For an HDMI-only update instead:
systemctl stop yunet-hdmi

# For an all/shared-interface update instead:
systemctl stop yunet-inference yunet-hdmi
```

Choose only the stop command matching your update. Leave the logged-in shell
idle and **close PuTTY** to release the port. Do not log out or power off the
board. Check free space with `df -h /tmp /opt` before a large transfer.

## 4. Transfer from the laptop over UART

In **laptop PowerShell**, from `D:\Github\FaceGuard\kv260-yunet`, run the
matching command. Replace `COM7` with your board's port:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\Deploy-Serial.ps1 -Component ml -Port COM7

# Or HDMI only:
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\Deploy-Serial.ps1 -Component hdmi -Port COM7

# Or both:
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\Deploy-Serial.ps1 -Component all -Port COM7
```

The helper defaults to `FaceGuard/.venv/Scripts/python.exe`; use its `-Python`
argument for another installed Python interpreter if needed. It checks the
archive file allowlist, refuses to replace a running selected component,
transfers through UART, verifies SHA256 and extracts into `/opt/yunet`.
Wait for **`SHA256 verified. Installed ...`** before reopening PuTTY. UART
transfer can take several minutes. This is an in-place update, not an atomic
or automatic rollback installation.

Errors before extraction leave the installed application unchanged. If an
installation is interrupted during extraction, keep the service stopped and
redeploy a complete known-good package.

## 5. Activate and verify on the board

Reopen PuTTY. For an ordinary executable/model update, start the selected
service:

```sh
# ML update:
systemctl start yunet-inference
systemctl status yunet-inference --no-pager -l
journalctl -u yunet-inference -n 60 --no-pager

# HDMI-only update instead:
systemctl start yunet-hdmi
systemctl status yunet-hdmi --no-pager -l
journalctl -u yunet-hdmi -n 60 --no-pager
```

After an `all` update, start `yunet-hdmi` first, then `yunet-inference`.
Verify live camera video, face boxes/landmarks with a face in view, and
camera-only video after `systemctl stop yunet-inference`. An active service
alone does not prove correct video or detections.

The UART helper extracts unit/config files under `/opt/yunet`; it does **not**
activate changed systemd units or the HDMI default configuration installed by
the OS image. Only if you intentionally changed those files, review and back
up the installed versions, then apply the selected files before restarting:

```sh
# ML unit, if changed:
cp /opt/yunet/service/yunet-inference.service /etc/systemd/system/yunet-inference.service

# HDMI unit/config, if changed (overwrites local HDMI settings):
cp /opt/yunet/service/yunet-hdmi.service /etc/systemd/system/yunet-hdmi.service
cp /opt/yunet/config/yunet-hdmi /etc/default/yunet-hdmi

systemctl daemon-reload
```

Run only the copies appropriate to your selected package. Units in
`/etc/systemd/system` override the image's vendor units; account for those
overrides in future OS updates. `daemon-reload` alone does not install a unit.
The ML configuration lives at `/opt/yunet/config/yunet.conf` and is replaced by
an ML package; preserve any local settings before deployment.

To roll back, stop the affected service, close PuTTY and deploy the previous
compatible archive using `Deploy-Serial.ps1 -Component ml -Port COM7
-Package <previous-ml-archive>` (or the matching HDMI/all selection). Restore
any changed installed unit/config files, reload systemd if needed, and restart.

Installed application changes persist across normal reboots. The image's
default policy still starts camera preview automatically and leaves ML manual.
Reflashing the card replaces these local updates.

## Model compatibility

The current model must match SmartCam B3136 DPU fingerprint
`0x101000016010406`. The application expects 320x320 INT8 NHWC BGR input and
twelve output heads at strides 8/16/32. A new architecture or tensor contract
requires coordinated preprocessing, inference validation and decoder changes.
A CPU ARM64 cross-compiler does not compile an ONNX model for the DPU; produce
a compatible `.xmodel` with the appropriate model compilation workflow first.

Update the model manifest, contract and pinned SHA256 checks when deliberately
changing the model. Image generation verifies the exact model hash; replacing
only the `.xmodel` will not satisfy those checks. Validate detections on hardware.

## Driver and platform updates

The application UART helper does not install `.ko` modules, kernels, device trees
or FPGA assets. A loadable module must match the running kernel release,
configuration and symbol versions; a built-in driver requires rebuilding the
kernel. This project does not provide a standalone driver-update helper.

For platform changes, edit the appropriate Yocto recipe/patch/config and run
in **laptop PowerShell**:

```powershell
cd D:\Github\yocto-image-builder
docker compose run --rm builder bash /project/scripts/image.sh kv260-vision-hdmi parse
docker compose run --rm builder bash /project/scripts/image.sh kv260-vision-hdmi build
```

Back up board data, flash the new `kv260-vision-hdmi.img`, boot it and validate
camera, HDMI and inference together. Keep the prior working SD/image for recovery.

## Include validated application changes in future images

After testing the application update, synchronize maintained source into this
repository and rebuild. Run in **laptop PowerShell**:

```powershell
cd D:\Github\FaceGuard\kv260-yunet
..\.venv\Scripts\python.exe .\tools\sync_image.py
cd D:\Github\yocto-image-builder
docker compose run --rm builder bash /project/scripts/image.sh kv260-vision-hdmi build
```

Review the generated source archive, release record and recipe changes before
committing them. For a release from committed FaceGuard source, use
`sync_image.py --require-clean`. Updating the board directly does not update
the source snapshot consumed by future image builds.
